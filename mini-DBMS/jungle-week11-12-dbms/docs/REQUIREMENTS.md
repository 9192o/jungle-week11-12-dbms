# 기능 요구사항

| 기능 | 설명 | 예시 |
| --- | --- | --- |
| **① 데이터 정의(DDL)** | 테이블과 데이터 구조 생성·수정·삭제 | `CREATE TABLE` |
| **② 데이터 조작(DML)** | 데이터 조회·삽입·수정·삭제 | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| **③ 무결성 관리** | 데이터가 정해진 규칙을 지키도록 보장 | 중복된 회원 ID 방지 |
| **④ 보안 및 접근 제어** | 사용자마다 데이터 접근 권한 설정 | 일반 사용자는 관리자 테이블 수정 불가 |
| **⑤ 트랜잭션 관리** | 여러 작업을 하나의 논리적 작업으로 관리 | 계좌이체 도중 실패하면 롤백 |
| **⑥ 동시성 제어** | 여러 사용자가 동시에 접근해도 데이터 일관성 유지 | 동시에 재고를 구매하는 상황 |
| **⑦ 백업 및 복구** | 장애가 발생했을 때 데이터 복구 지원 | 서버 장애 후 로그를 이용한 복구 |

## Phase 1. SQL 처리기

> **SQL 파일을 CLI 인자로 받아, SQL을 파싱하고 CSV 파일에 데이터를 쓰거나 읽는 처리기를 구현한다.**
> 
1. **CLI 입력 처리**
    - 프로그램은 명령줄 인자로 SQL 파일 경로를 전달받아야 한다.
    - SQL 처리기가 지정한 파일을 열고 SQL 문을 읽을 수 있어야 한다.
    - 하나의 SQL 파일에 여러 SQL문이 포함될 수 있어야 한다.
        - 여러 SQL 문은 세미콜론(`;`)으로 구분한다.
        - 문자열 리터럴 내부의 세미콜론은 SQL 문 구분자로 취급하지 않아야 한다.
        - SQL 문은 파일에 작성된 순서대로 실행되어야 한다.
    - SQL 파일이 존재하지 않거나 읽을 수 없는 경우 오류를 반환해야 한다.
2. **SQL 파싱**
    - SQL 문을 분석해서 실행기가 사용할 수 있는 내부 표현으로 변환해야 한다.
        - `INSERT INTO`, `VALUES`, `SELECT`, `FROM`, `WHERE`를 지원한다.
        - `INSERT`에서 테이블명, 컬럼 목록(선택), 값 목록을 추출한다.
        - `SELECT`에서 대상 테이블 및 검색 조건을 추출한다.
        - `WHERE`는 단일 조건의 동등 비교(`=`)만 지원한다.
        - 문자열, 정수 리터럴을 구분해야 한다.
        - 키워드는 대소문자 구분 없이 처리한다.
        - 문자열 내부의 공백, 쉼표, 이스케이프된 작은따옴표를 올바르게 처리한다.
        - 지원하지 않는 SQL 구문은 명시적인 오류를 반환한다.
    - SQL 문법 예시는 다음과 같다.
        
        ```sql
        INSERT INTO students VALUES (1, '민수', 20);
        
        INSERT INTO students (id, name, seat)
        VALUES (2, '철수', 21);
        
        SELECT * FROM students;
        
        SELECT * FROM students WHERE id = 1;
        
        SELECT * FROM students WHERE name = '민수';
        ```
        
3. **SQL 실행**
    - SQL 실행기는 파싱된 명령에 따라 `INSERT` 또는 `SELECT`를 수행해야 한다.
    - `INSERT`는 지정된 테이블 파일에 레코드를 추가한다.
    - `SELECT`는 테이블 파일을 읽어 조건에 부합하는 레코드를 반환한다.
        - `WHERE`가 없는 `SELECT`는 테이블의 전체 레코드를 반환한다.
        - 검색 결과가 없으면 빈 결과를 반환한다.
    - 실행 결과와 오류를 구분하여 터미널에 출력해야 한다.
    - 한 SQL 문에서 오류가 발생하더라도 이후 SQL 문은 계속 실행한다.
    - 오류가 발생한 문장의 순번과 원인을 출력하며, 하나라도 실패했다면 프로그램의 최종 종료 코드는 실패를 나타내야 한다.
4. **CSV 파일 기반 저장**
    - 테이블마다 별도의 CSV 파일을 사용한다.
    - 파일명과 테이블명은 사전에 정의된 매핑에 따라 연결한다.
        - CSV 파일의 첫 번째 행은 스키마로 사용한다.
        - 각 컬럼의 이름과 데이터 타입을 스키마에서 확인할 수 있어야 한다.
    - CSV 파일의 문자 인코딩은 UTF-8로 통일한다.
    - 하나의 물리적 줄에 하나의 레코드를 저장한다.
    - 문자열 내부의 쉼표는 CSV 인용 규칙에 따라 처리한다.
    - 구현 범위를 단순화하기 위해 필드 내부 줄바꿈은 지원하지 않는다.
    - 프로그램 종료 후 다시 실행하더라도 이전에 저장한 데이터를 조회할 수 있어야 한다.
    - 자료형을 넣는다면 첫 줄에 같이 넣는다. (`id : int`)
    - `INSERT`가 저장한 데이터를 이후 실행에서 `SELECT`로 읽을 수 있어야 한다.
    - CSV 예시는 다음과 같다.
        
        ```
        id:int,name:string,seat:int
        1,민수,20
        2,철수,21
        ```
        
5. **전제와 구현 범위**
    - 지정한 테이블이 존재하는지 확인해야 한다.
    - 지정한 컬럼이 스키마에 존재하는지 확인해야 한다.
    - `INSERT` 시 값의 개수와 컬럼의 개수가 일치해야 한다.
    - 입력값이 스키마의 데이터 타입에 적합한지 검증해야 한다.
    - `id` 컬럼은 정수이며 중복을 허용하지 않는다.
    - 스키마를 만족하지 않는 레코드는 저장하지 않아야 한다.
    - CSV 파일이 유효하지 않거나 I/O 오류가 발생하면 해당 오류를 보고해야 한다.
    - 잘못된 테이블 이름으로 테이블 디렉터리 외부의 파일에 접근할 수 없어야 한다.
    - `CREATE TABLE`은 구현 범위에서 제외한다.
6. **Phase 1 완료 기준**
    - [x]  하나의 SQL 파일에서 여러 SQL 문을 순서대로 실행한다.
    - [x]  정상적인 `INSERT` 이후 CSV 파일에 레코드가 추가된다.
    - [x]  `SELECT`로 전체 또는 조건에 맞는 레코드를 조회할 수 있다.
    - [x]  프로그램을 종료한 뒤 재실행해도 기존 데이터가 유지된다.
    - [x]  잘못된 SQL, 타입 불일치, 중복 ID를 검출한다.
    - [x]  실패한 삽입으로 불완전한 레코드가 남지 않는다.

## Phase 2. B+ Tree 구현과 성능 비교

> **Phase 1 SQL 처리기에 메모리 기반 B+ Tree를 이용하여 ID 검색을 최적화하고, 선형 탐색과 인덱스 탐색의 성능 차이를 측정한다.**
> 
1. **메모리 기반 B+ 트리 구현**
    - 프로그램을 시작할 때 기존 CSV 데이터를 해석하여 B+ 트리를 구성해야 한다.
    - 테이블마다 독립적인 B+ Tree를 유지한다.
    - B+ Tree의 키는 레코드의 `id`로 한다.
        - 값은 해당 레코드가 저장된 CSV 파일의 시작 바이트 오프셋으로 한다.
        - 새로운 키와 오프셋을 삽입하고, ID로 레코드의 파일 위치를 찾을 수 있어야 한다.
        - 키는 정렬된 상태를 유지해야 한다.
        - 노드의 분할 및 상위 노드 갱신을 지원해야 한다.
        - 모든 리프 노드는 동일한 깊이에 있어야 한다.
    - 중복 키 삽입은 거부해야 한다.
    - 존재하지 않는 키를 검색하면 검색 실패를 반환해야 한다.
    - 인덱스 구축이 완료된 후 SQL 요청을 처리해야 한다.
    - 인덱스를 구축하는데 걸린 시간을 측정할 수 있어야 한다.
    - 인덱스가 메모리에서 사라지더라도 CSV 파일을 이용해 재구축할 수 있어야 한다.
    
2. **`INSERT` 시 ID 자동 부여**
    - 새 레코드마다 같은 테이블 안에서 중복되지 않는 ID를 자동으로 생성할 수 있어야 한다.
        - ID는 해당 테이블의 현재 최댓값 ID + 1로 설정한다.
        - ID는 각 테이블에서 독립적으로 관리한다.
        - 기존 데이터가 없으면 ID는 1부터 시작한다.
        - ID 자동 부여 시 해당 컬럼을 생략한 `INSERT` 문을 허용한다.
            
            ```sql
            INSERT INTO students (name, seat)
            VALUES ('민수', 20);
            ```
            
        - 명시적으로 ID를 지정하는 기존 Phase 1의 `INSERT`도 지원한다.
        - 명시된 ID가 중복되면 삽입을 거부한다.
        - ID의 자동 부여와 파일 쓰기 및 인덱스 등록은 일관된 하나의 삽입 작업으로 관리한다.
    - ID를 포함한 레코드를 Phase 1에서 사용한 테이블 파일에 저장한다.
        - `INSERT`할때 트리 노드에 파일 위치의 시작 오프셋을 저장한다.
        - 트리 노드를 `key`로 찾고, `value`의 시작 오프셋을 읽어 파일의 시작 위치를 알아낼 수 있어야 한다.
    - 저장한 레코드의 ID와 위치를 B+ 트리에 등록한다.
    - 삽입에 실패하면 해당 작업이 파일과 인덱스에 불일치한 상태로 남지 않도록 처리해야 한다.
    
3. **`SELECT`에 두 가지 검색 방식 연결**
    - `WHERE id = 값` 형태의 조회는 B+ Tree를 이용해야 한다.
    - B+ Tree에서 찾은 오프셋으로 이동하여 대상 레코드를 읽어야 한다.
    - 인덱스가 없는 다른 컬럼은 선형 탐색으로 검색한다.
    - `WHERE`가 없는 `SELECT`는 전체 파일을 순차적으로 읽는다.
    - 동일한 조건에 대해 인덱스 검색과 선형 탐색은 동일한 결과를 반환해야 한다.
    - 검색 예시는 다음과 같다.
        
        ```sql
        SELECT * FROM students WHERE id = 42; 
        → **B+ 트리**에서 ID `42`의 위치를 찾아 해당 레코드를 읽는다.
        
        SELECT * FROM students WHERE name = '민수'; 
        → 파일의 레코드를 **앞에서부터 하나씩 읽어** 이름이 일치하는 행을 찾는다.
        ```
        
    
4. **Phase 1 SQL 처리기와 연동**
    - 기존 CLI로 SQL 텍스트 파일을 받아 실행하는 흐름을 재사용한다.
    - 기존 `INSERT` 실행 흐름에 ID 부여와 인덱스 등록을 추가한다.
    - `SELECT` 실행 흐름에서 조건에 따라 검색 방식을 선택한다.
    - CLI를 실행할 때마다 새 프로세스가 시작되는 구조라면, 기존 파일에 저장된 레코드도 검색할 수 있게 메모리 인덱스를 구성한다. 예를 들어 시작할 때 파일을 한 번 읽어 B+ 트리를 다시 만들 수 있다.

1. **성능 테스트**
    - 테스트 데이터를 자동으로 생성해 레코드 **1,000,000개 이상**을 삽입한다.
    - 같은 테이블에서 **ID 인덱스 검색**과 **다른 필드의 선형 검색** 시간을 비교한다.
    - 순수 조회 속도를 비교할 때는 **인덱스를 만드는 시간과 조회 시간을 따로 기록**한다. 두 쿼리가 비슷한 수의 행을 반환하도록 데이터를 골라 출력량 차이도 줄인다.
    - 대량 데이터에서 B+ Tree 인덱스 생성 시간을 측정해야 한다.
    - ID 조회에 대해 인덱스 사용과 미사용의 실행 시간을 비교해야 한다.
    - 인덱스가 없는 컬럼의 선형 탐색 시간도 별도로 측정해야 한다.
    - 조회 결과의 일치 여부를 검증해야 한다.
    - 조회 위치에 따른 차이를 확인하기 위해 앞부분, 중간, 끝부분, 존재하지 않는 ID를 사용한다.
    - 동일한 조건에서 여러 번 측정하고 평균 또는 중앙값을 기록한다.
    - 인덱스 구축 시간, 순수 조회 시간, 결과 출력 시간을 구분한다.

1. **Phase 2 완료 기준**
    - [x]  B+ Tree 삽입 및 검색이 정상 동작한다.
    - [x]  노드 분할 이후에도 모든 데이터가 검색된다.
    - [x]  ID와 CSV 파일의 바이트 오프셋이 정확히 연결된다.
    - [x]  INSERT 이후 새로운 레코드를 인덱스로 조회할 수 있다.
    - [x]  프로그램 재실행 시 기존 CSV 데이터로 인덱스를 복원한다.
    - [x]  중복 ID가 발생하지 않는다.
    - [x]  100만 건 이상에서 인덱스 검색과 선형 검색을 비교한다.
    - [x]  인덱스 사용 여부와 실행 시간을 검증할 수 있다.

## Phase 3. API 서버 및 동시성 제어

> **Phase 1, 2에서 만든 DBMS를 API 서버에 연결해서, 외부의 여러 요청을, 동시에 일관성 있게 처리할 수 있게 만든다.**
> 
1. **API 제공**
    - FastAPI를 통해 외부 클라이언트가 SQL 요청을 전달할 수 있어야 한다.
        - API 요청 단위로 하나의 SQL 문을 처리한다.
        - API는 SQL 문을 DBMS의 기존 파서와 실행기에 전달한다.
    - `INSERT` 성공 시 성공 여부와 삽입된 ID를 반환한다.
    - `SELECT` 성공 시 조회된 데이터를 구조화된 형태로 반환한다.
    - SQL 구문 오류, 제약조건 위반, 실행 실패에 대해 오류를 반환한다.
        - 응답 형식과 오류 코드는 일관된 구조를 가져야 한다.
    - API 예시는 다음과 같다.
        
        ```json
        POST /query
        Content-Type: application/json
        
        요청:
        {
          "sql": "SELECT * FROM students WHERE id = 42;"
        }
        
        응답:
        {
          "success": true,
          "columns": ["id", "name", "seat"],
          "rows": [[42, "민수", 20]]
        }
        ```
        
2. **기존 DBMS 연동**
    - Phase 1의 SQL 파서와 실행기를 재사용해야 한다.
    - Phase 2의 B+ Tree 구현을 재사용해야 한다.
    - API 요청 처리 과정에서 별도의 SQL 파서나 저장 로직을 중복 구현하지 않아야 한다.
    - 서버 시작 시 CSV 파일을 기반으로 인덱스를 구성해야 한다.
        - 동일한 서버 프로세스의 요청들은 테이블과 인덱스 상태를 공유해야 한다.
    - `INSERT`는 기존 흐름대로 ID를 자동 부여하고, 테이블 파일에 저장한 뒤 B+ 트리에 등록한다.
    - `WHERE id = ?`는 B+ 트리로 검색하고, 인덱스가 없는 필드는 기존 선형 탐색으로 처리한다.
    - SQL 요청의 실행 결과는 CLI와 API에서 동일한 의미를 가져야 한다.

1. **스레드 풀 기반 요청 처리**
    - 서버는 제한된 수의 작업 스레드를 준비하고 사용해야 한다.
        - 스레드 수는 설정값으로 관리할 수 있어야 한다.
        - 작업 스레드는 요청 처리가 끝나면 재사용되어야 한다.
        - 여러 SQL 요청을 스레드 풀에서 처리할 수 있어야 한다.
    - 들어온 SQL 요청을 스레드 풀에 넘기면, 사용 가능한 스레드가 처리한다.
        - 동시에 들어온 요청은 서로 다른 스레드에서 처리할 수 있어야 한다.
    - 스레프 풀 용량을 초과하는 요청은 정의된 대기 또는 거부 정책에 따라 처리해야 한다.
    
2. **테이블 단위 동시성 제어와 일관성**
    - 각 테이블은 독립적인 읽기·쓰기 락을 가져야 한다.
        - 같은 테이블의 요청은 이 락을 공유한다.
    - `INSERT`는 쓰기 락을 얻은 뒤 ID를 확인하거나 발급한다.
        - 파일 쓰기와 인덱스 갱신이 끝날 때까지 락을 유지해야 한다.
        - 실패하면 복구하거나 테이블을 사용 불가로 표시한 뒤 락을 해제해야 한다.
        - 여러 사용자가 동일한 테이블에 동시에 `INSERT`를 요청할 수 있어야 한다. 같은 테이블의 쓰기 락은 한 요청만 보유할 수 있다.
        - 자동 생성된 ID가 중복되지 않아야 한다.
        - 파일에 기록되는 레코드가 서로 섞이거나 손상되지 않아야 한다.
        - 삽입에 성공한 모든 레코드가 B+ Tree에 등록되어야 한다.
        - 성공한 삽입 작업의 결과는 이후 조회에서 확인할 수 있어야 한다.
        - 파일 기록 또는 인덱스 갱신 실패 시 불일치를 감지하고 복구하거나, 해당 테이블의 추가 요청을 안전하게 중단해야 한다.
    - `SELECT`는 인덱스와 파일을 읽는 동안 읽기 락을 유지해야 한다.
        - 쓰기 락과 읽기 락은 같은 테이블에서 동시에 보유할 수 없다. `INSERT`와 `SELECT`가 동시에 요청돼도 조회는 부분적으로 기록된 데이터를 반환해서는 안 된다.
        - 인덱스가 가리키는 파일 위치는 유효한 레코드여야 한다.
        - 쓰기 락을 사용 중이거나 기다리는 요청이 없고 작업 스레드에 여유가 있으면, 같은 테이블의 여러 `SELECT`가 읽기 락을 함께 보유해 동시에 진행할 수 있어야 한다.
        - 여러 `SELECT` 요청이 동시에 실행돼도 각 요청은 정확한 결과를 반환하고 저장 데이터는 유지되어야 한다.
        - 동일한 테이블에 대한 읽기와 쓰기는 정의된 락 정책을 따라야 한다.
    - 서로 다른 테이블에 대한 작업은 독립적으로 진행할 수 있어야 한다.
    - 요청 처리 중 오류가 발생해도 락이 해제되어야 한다.
    
3. **외부 요청부터 응답까지 검증**
    - 허용된 SQL 구문만 실행할 수 있어야 한다.
    - 클라이언트가 전달한 테이블명이 임의의 파일 경로로 해석되지 않아야 한다.
    - 단일 요청의 최대 SQL 길이를 제한할 수 있어야 한다.
    - API는 개발 및 테스트 환경에서 사용하며, 인증 없이 공용 인터넷에 노출하지 않는다.
    - API에서 `INSERT` 후 `SELECT`로 데이터를 조회할 수 있어야 한다.
        - API를 통한 `WHERE id = ?` 조회가 실제로 B+ 트리를 사용하는지 확인한다.
        - 인덱스 기반 조회가 실제 B+ Tree를 경유하는지 확인해야 한다.
    - 같은 테이블에 여러 `INSERT`를 동시에 보내고, 모든 성공 응답에 해당하는 행이 서로 다른 ID로 저장됐는지 확인한다.
        - 동시 `INSERT`와 `SELECT` 상황에서 불완전한 레코드가 반환되지 않아야 한다.
    - 서버를 정상 종료한 후 재실행하여 저장된 레코드를 다시 조회할 수 있어야 한다.
    - 서로 다른 테이블에 대한 작업이 독립적으로 처리되는지 확인해야 한다.

1. **Phase 3 완료 기준**
    - [x]  브라우저 또는 외부 클라이언트가 API를 호출할 수 있다.
    - [x]  기존 SQL 파서 및 실행기를 재사용한다.
    - [x]  스레드 풀에서 여러 요청을 처리한다.
    - [x]  동시 INSERT에도 ID 중복이 없다.
    - [x]  동시 조회 중 부분적으로 기록된 데이터가 반환되지 않는다.
    - [x]  서로 다른 테이블의 처리가 독립적이다.
    - [x]  정상 재시작 후 데이터 및 인덱스를 복원한다.

# 비기능 요구사항

- 100만 건 이상의 레코드를 처리할 수 있어야 한다.
- 정상 종료 후에도 저장된 데이터가 유지되어야 한다.
- 인덱스 조회와 선형 조회의 실행 시간을 측정할 수 있어야 한다.
- 스레드 간 데이터 경합으로 파일과 인덱스가 손상되지 않아야 한다.
- SQL 파서, 실행기, 저장소, 인덱스는 역할별로 분리되어야 한다.
- 실행 실패 시 오류 원인을 추적할 수 있어야 한다.
- 파일의 인코딩과 레코드 형식은 일관되어야 한다.
