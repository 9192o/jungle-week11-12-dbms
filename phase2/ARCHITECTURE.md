# Phase 2. B+ Tree, 자동 ID, 바이트 오프셋

## 범위와 SQL 계약

- Phase 1의 CLI, SQL 파싱, 등록된 테이블만 접근하는 카탈로그, 타입이 명시된 UTF-8 CSV 형식을 이어받는다. 이 문서에서 정한 INSERT와 정수 범위는 Phase 2에 적용한다.
- CSV는 LF만 허용하며, 필드 내부의 CR/LF는 거부한다. 마지막 레코드에 LF가 없어도 읽을 수 있다. 헤더만 있고 LF가 없는 파일도 빈 테이블로 읽는다.
- SQL 파일은 명령줄 인자로 받고 문장을 파일 순서대로 실행한다. 결과는 표준출력, 오류는 표준에러로 보낸다. 실패한 문장의 순번과 원인을 보고한다. 처리 도중 실패가 하나라도 있으면 종료 코드는 1이다.
- `phase2` 디렉터리에서 `python -B mini-dbms/cli.py query.sql`로 실행한다. 기본 카탈로그는 `users`를 `./tables/users.csv`에 연결한다.
- Phase 2에서는 실행 중 다른 프로세스가 CSV를 수정하지 않는다고 전제한다. 동시 접근을 위한 락은 Phase 3에서 다룬다.

| SQL | 동작 |
| --- | --- |
| `INSERT INTO users (name, seat) VALUES ('민수', 20);` | 열 목록은 필수다. `record_id`를 제외한 모든 열을 한 번씩 지정하며, 저장할 값은 스키마 순서로 재배치한다. `record_id`는 DB가 자동 부여한다. |
| `INSERT INTO users VALUES (...);` | 열 목록이 없으므로 파일을 변경하지 않고 실패한다. |
| `INSERT INTO users (record_id, name, seat) VALUES (...);` | `record_id`를 직접 지정했으므로 파일을 변경하지 않고 실패한다. |
| `SELECT ... FROM users WHERE record_id = 값;` | B+ Tree에서 `record_id`를 찾고, 적중하면 CSV의 대상 행을 읽는다. |
| 다른 열의 동등 조건 또는 조건 없는 `SELECT` | CSV를 순차적으로 읽는다. |

- `int` 열의 값과 SQL 정수 리터럴에는 64비트 `unsigned long long` 범위인 `0`부터 `2^64 - 1`(`18446744073709551615`)까지를 적용한다. 범위 밖 SQL 입력은 문장 오류, 범위 밖 CSV 값은 저장소 오류다.
- 테이블에 행이 없으면 첫 자동 `record_id`는 1이다. 그 외에는 해당 테이블의 현재 최대 `record_id`에 1을 더해 부여한다. 자동 발급 최솟값은 1이다. 현재 최대값이 `2^64 - 1`이면 CSV나 인덱스를 변경하기 전에 INSERT를 실패 처리한다.

## 인덱스 구축과 조회

1. CLI 시작 시 카탈로그에 등록된 각 CSV를 바이너리 모드로 연다. 스키마 헤더를 검증한 뒤 각 행을 읽기 직전의 `tell()`을 행의 시작 바이트 위치로 사용한다.
2. 각 행을 UTF-8로 해석해 모든 열을 검증하고, `record_id → 바이트 오프셋`을 해당 테이블의 메모리 B+ Tree에 저장한다. 테이블별 최대 `record_id`도 함께 기록한다. 재실행할 때 CSV에서 다시 구축한다.
3. CSV 읽기·검증 오류나 중복 `record_id`가 있으면 표준에러에 테이블명과 구축 실패 원인을 출력하고 해당 테이블의 읽기와 쓰기를 차단한다. 구축 오류에는 SQL 문장 순번을 붙이지 않는다. 다른 테이블은 계속 구축하고 실행하며, 최종 종료 코드는 1이다.
4. ID 조회는 요청 열과 조건값의 타입을 확인한 뒤 인덱스를 검색한다. 일치하는 키가 없으면 열 목록과 빈 행 목록을 반환한다. CLI는 헤더만 출력한다.
5. 키가 있으면 해당 오프셋으로 이동해 한 줄을 읽고 모든 열을 검증한다. 행을 읽을 수 없거나 잘못된 행이거나 읽은 `record_id`가 검색 키와 다르면 저장소 오류로 처리한다.
6. 같은 ID 조건의 강제 순차 조회는 테스트와 벤치마크에서만 사용한다. 일반 CLI 실행의 ID 조회는 B+ Tree를 사용한다.

## B+ Tree 노드와 분할

- 최대 키 개수의 기본값은 노드당 128개다. 분할 테스트에서는 최대 키 개수를 3개로 설정한다.
- 리프에만 `(record_id, 바이트 오프셋)`을 저장한다. 내부 노드는 구분 키를 저장하며 키가 `K`개이면 자식은 `K+1`개다.
- 구분 키는 오른쪽 자식 서브트리의 최소 키다. 검색 키가 구분 키와 같으면 오른쪽으로 내려간다. 동일한 `record_id` 삽입은 기존 값을 변경하지 않고 거부한다.
- 노드가 최대 키 개수를 넘으면 가운데를 기준으로 나눈다. 리프 분할에서는 오른쪽 리프의 첫 키를 부모에 복사한다. 내부 노드 분할에서는 넘친 키 목록에서 0부터 세어 `키 개수 // 2` 위치의 구분 키를 자식 노드에서 빼고 부모로 올린다.
- 부모도 용량을 넘으면 분할한다. 루트가 나뉘면 새 루트를 만들며 모든 리프의 깊이는 동일하게 유지한다.

## INSERT와 실패 복원

1. 테이블과 열 목록을 확인하고 새 값의 타입을 검증한다. 시작할 때 기존 CSV를 전부 검증하므로 정상 INSERT에서 기존 행을 다시 순회하지 않는다.
2. 자동 `record_id`를 계산하고 인덱스로 중복 여부를 확인한다. 새 레코드를 UTF-8 바이트로 변환하고 쓰기 직전의 EOF를 기록한다.
3. 파일 끝에 레코드를 추가한다. 마지막 레코드 또는 헤더에 LF가 없어 구분 LF를 먼저 추가하면 새 행의 시작 오프셋은 `이전 EOF + 1`이다. 그 외에는 `이전 EOF`다.
4. 파일 쓰기와 `flush`, B+ Tree 등록이 모두 끝나면 최대 ID를 갱신하고 성공 처리한다.
5. 쓰기 또는 트리 등록에 실패하면 파일을 이전 EOF로 복원한다. 트리 변경이 시작됐다면 변경 중인 인덱스를 폐기하고, 복원한 CSV로 인덱스와 최대 ID를 재구축한다.
6. 파일 복원이나 재구축을 확인할 수 없으면 현재 CLI 실행에서 해당 테이블의 읽기와 쓰기를 차단한다. 이 절의 복원은 실행 중 감지한 오류를 대상으로 한다.
